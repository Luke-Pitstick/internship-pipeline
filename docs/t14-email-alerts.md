# T14 — Optional SMTP alerts and daily digests

Implemented October 6, 2026. The owner can configure SMTP through Settings → Notifications & Integrations, save an encrypted password, request a synthetic test message, choose individual alerts or a daily digest, set a score threshold/hour/IANA timezone, request available PDFs, and enable or disable automatic delivery. Saving does not send a message. SMTP using STARTTLS or implicit TLS is the supported provider flow; this is not a claim of arbitrary Apprise provider configuration.

## Delivery and data contract

`EmailIntegrations` uses the existing jobs SQLite database and existing `tasks` queue with `email_delivery` tasks. The independently supervised `email-delivery` role scans current persisted recommended assessments for open, unapplied jobs above the configured score, suppressing dismissed or owner-rejected jobs. Collection, matching and résumé generation are never rerun by SMTP failures. Digest membership and delivery/attempt records persist in `email_members`, `email_deliveries` and `email_attempts`. The configured local hour is evaluated with Python IANA timezone rules and a direct `tzdata` runtime dependency; the durable local-day check prevents a second digest during a repeated DST hour. At most 100 jobs enter one digest; the remaining unseen jobs enter later digests. Empty digests are omitted.

Destinations keep their nonsecret fields and optimistic revision in `email_config`; passwords use the existing Fernet cipher and exact `model-credentials.key`. APIs never return passwords or raw transport exceptions. The key guard includes integration-only credentials so losing that key cannot silently create an unreadable replacement. T17 backs up this same database and key. The owner-session, CSRF and origin boundaries protect read/save/test/retry. There is a five-test-per-hour limit.

Accepted means Apprise acknowledged acceptance, not human receipt. Explicit transport rejection gets shared-queue backoff, capped at three attempts. Apprise false responses, unexpected errors or interrupted in-flight attempts are uncertain, require attention and are never replayed automatically. The UI labels a deliberate retry as potentially duplicating a remote email. This is intentionally not exactly-once SMTP delivery. Configuration changes cancel queued/retrying work and release its unsent membership; disabling may allow a send that was already in flight to finish.

Alerts include stable job ID, source timestamp and first-observed timestamp separately, fit and the application URL. Notification time is stored separately. No alert submits or marks an application Applied. PDFs are optional: the shared app/worker attachment resolver uses only the current tailored document and its validated private-byte reader. Missing, stale or unavailable PDFs do not block alerts. SMTP attachment support is checked through Apprise; up to ten PDFs of at most 5 MB each are temporarily materialized as private files, and the temporary directory is removed after sending.

## Verification and limits

Ten focused Python tests pass, including real current-assessment selection, encrypted-at-rest/redacted settings, queue and restart deduplication, timezone digest membership, ambiguous interruption without automatic replay, deliberate retry, bounded rejection retries, disable/cancellation, optional PDF behavior, applied/stale suppression, missing-key protection and the mounted authenticated API with CSRF/logout checks. Ruff and mypy pass for both new backend modules and the secret-store guard. Svelte check reports zero errors/warnings and the production static build passes.

One dedicated Chromium test passes against the real temporary FastAPI owner API and independent delivery worker. Its SMTP transport is synthetic and acknowledges without contacting a provider. The browser claims the owner, saves friendly SMTP fields and digest/timezone controls, verifies the password field clears, queues the test, observes accepted status, disables delivery and checks a 390 px layout without horizontal overflow. Reproduce with `rtk proxy env PYTHONPATH=src .venv/bin/pytest tests/test_email_integrations.py -q` and, from `web/`, `rtk proxy npx playwright test --config playwright.email.config.ts` after a build. Its temporary server requires local listener permission in the sandbox. Native mocked SMTP acceptance is not live receipt.

Live SMTP acceptance is explicitly blocked: no authorized mailbox credential or recipient test was provided, and this task sends no external messages. Retrying requires a supported SMTP credential and explicit authorization to send the bounded synthetic test, then confirmation of receipt and optional PDF attachment through this same path. The Docker engine remains unavailable; native browser/worker evidence does not establish actual container operation.
