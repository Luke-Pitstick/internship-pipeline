## Diagnostic behavior

Settings → Diagnostics exposes source last attempt/success and freshness age, queue counts, active leases and activity timestamps, supervisor heartbeat/active roles, model-attempt statuses, failed work and a bounded sanitized event view. Missing/stale supervisor state is visibly degraded, never silently called healthy. All raw task/provider exception text is replaced with application-owned messages; model statuses use an allowlist. The owner can deliberately retry recoverable local work with session/CSRF/origin enforcement. External delivery and Sheets synchronization require their own integration's review/retry or fresh preview, so a generic retry cannot resend an uncertain side effect. Job application submission remains separate.

## Backup contract

`backup` captures **both** jobs and identity SQLite databases through SQLite's backup API after obtaining an exclusive installation lock. It includes the exact `model-credentials.key`, effective settings, configured company/search registries, the configuration directory, retained upload provenance/extracted sources in the jobs database, any existing uploads directory, and the entire configured artifact directory (master and tailored documents). Current T10 retains extraction and provenance in SQLite rather than keeping every original uploaded binary; backups preserve every retained source/evidence record and any operator-retained upload files. Email and Sheets credentials/configuration/accepted deliveries/journals/checkpoints live in the same jobs database and use that exact key.

The application factory, lifespan, bootstrap, CLI commands and workers hold shared locks while they can write. Backup refuses to proceed while these supported runtimes are active. Stop the service and all workers first. Direct unsupervised Python scripts that bypass application/CLI entry points are outside this stopped-instance contract; stop them too. A running-instance copy is intentionally unsupported. The two sequential snapshots are coherent because every supported writer is stopped, and SQLite incorporates committed WAL content into standalone snapshots without copying WAL/SHM files.

The private output directory has a versioned manifest covering every saved file's size and SHA-256. Before publishing, backup checks both databases and verifies that the saved key decrypts model, SMTP and Sheets secrets. Symlinks and nonregular files fail. Existing outputs and installation paths cannot be overwritten; temporary incomplete snapshots are cleaned on errors. Treat the entire backup as secret recovery material: the key and encrypted credentials are present together, and the documents/identity database are private. Restrict the directory to the owner, and keep an encrypted offline copy if moving it off the host.

Use the installed CLI, or the repository's Python environment with `PYTHONPATH=src`:

```sh
internship-pipeline backup /private/backups/pipeline-2026-10-06 --data-dir /private/pipeline
internship-pipeline restore /private/backups/pipeline-2026-10-06 /private/pipeline-restored
```

The example paths are placeholders. `--config /path/settings.yaml` before `backup` selects an explicit infrastructure config; otherwise backup reads `<data-dir>/config/settings.yaml` and the same runtime defaults as the application. The destination must be new and outside the source installation. In a stopped Docker installation, run this CLI in a one-off container with the stopped data volume and a separate private backup mount; use `--data-dir /var/data`. Do not remove the data volume. That container command remains unverified until Docker responds.

## Fresh restore and owner recovery

Restore validates the manifest, both databases, copied bytes and credential decryption before exposing a new installation. It refuses an existing destination or a destination inside the source backup. Effective paths are written into the restored `config/settings.yaml`, pointing at the fresh jobs database, registries and artifact directory. Launch the application with `PIPELINE_DATA_DIR` set to the restored directory and its config selected; set the installation's public origin/web assets/service environment for the destination host. Host-specific public origin and service-manager settings are not secret database state and must be selected for that host.

Restore retains source timestamps, observation identities, settings/model/profile revisions, upload provenance, generation manifests, assessments, explicit application records, complete task states and confirmed delivery ledgers. Revision-aware assessment reads still suppress old evaluations after a profile revision changes. No ingestion/re-evaluation is performed as a side effect of restore, so no duplicate jobs are created. In-flight tasks become failed with `restore_interrupted_work_requires_review`; in-flight email becomes uncertain and in-flight Sheets requires a fresh preview. Confirmed email and completed Sheets state/journals survive and are not automatically replayed. Unknown model usage remains reserved in the run ledger. Owner passwords remain valid, but browser sessions are revoked so the restored host requires a fresh sign-in.

If the owner password is lost, use the **local** operator console:

```sh
internship-pipeline recover-owner --data-dir /private/pipeline-restored
```

The command prompts for a username and the password twice; credentials are not command-line arguments. It atomically replaces the password hash and revokes all sessions. It needs local access to the private data directory and does not create a public recovery endpoint. First-run setup tokens cannot reclaim an already-owned installation. If the credential key is missing, restore the complete private backup; generating a replacement key cannot recover old connections.
