## Prepared image and CI

The Dockerfile builds and checks the locked Svelte frontend on the build host, then installs the frozen Python lock and TeX in the target-platform Python 3.12 Bookworm image. Runtime contains the built frontend, Python application/dependencies and renderer. It runs as UID 10001, declares one `/var/data` volume, exposes port 8080 and includes a readiness healthcheck. Compose adds init, a read-only root, `/tmp` tmpfs, a loopback-only published port and a 45-second graceful-stop window. `PIPELINE_PORT=18080` now derives `PIPELINE_ORIGIN=http://localhost:18080` unless the operator deliberately overrides the origin; its healthcheck sends that configured Host header.

The build context permits only package/lock files, Python source and the frontend source/static/build configuration. Host `.env`, candidate files, source registries, runtime databases, artifacts, credentials, documentation, test fixtures and browser reports are excluded. The recovery fixture is mounted only during isolated acceptance; it is not copied into the image. The image never receives host model/SMTP/Google environment credentials. The three build arguments contain only package version, Git revision and repository URL.

`.github/workflows/checks.yml` retains Python lint/types/tests/wheel validation, removes the obsolete demo invocation, and adds locked frontend installation, Svelte check, build, bundle budget and Chromium tests. `.github/workflows/container-images.yml` is a reviewable **candidate** workflow triggered by relevant pull requests or explicit manual dispatch. It uses native `ubuntu-24.04` amd64 and `ubuntu-24.04-arm` arm64 runners, asserts the loaded image's architecture, then runs the same isolation/recovery acceptance on Docker and rootless Podman. Failure on either engine prevents that platform's OCI candidate export.

Successful jobs export `internship-pipeline:<package-version>-<architecture>` OCI tar artifacts with SBOM and maximum provenance, the source/dependency locks, candidate SHA-256 and measured host evidence. A config-digest comparison rejects an OCI export that does not contain the exact smoke-tested image. Loading an image into Docker does not retain attestations, so the separate OCI export carries them. No registry login, `packages: write`, tag event, registry push, mutable `latest` reference or release publication step is configured. No CI run has been dispatched in this session. A successful pair of future CI runs would supply native execution evidence and separate candidates; it would still need review and authorized registry publication/combined manifest before a multiarchitecture registry reference exists. See the official [native runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), [Docker attestation rules](https://docs.docker.com/build/ci/github-actions/attestations/), and [OCI exporter](https://docs.docker.com/build/exporters/oci-docker/).

## Run the actual acceptance on a healthy host

From the project root, with a responsive local engine:

```sh
rtk proxy python3 deploy/container-smoke.py --recovery --report /tmp/pipeline-docker-evidence.json
```

For an already built local image, add `--image internship-pipeline:0.1.0-arm64 --platform linux/arm64`. That image is inspected and retained; the runner does not pull or remove an operator-supplied image. `--engine podman` selects the installed Podman CLI; this is a test capability, not a current support claim. Every engine operation has a timeout, and preflight precedes resource creation. Build defaults to 1,200 seconds and readiness to 60 seconds. Engine output, setup token, password, cookie and application logs are captured privately and never printed. The runner removes only its uniquely generated containers, volumes and locally built image tag, and names its own remaining resources if cleanup fails.

The initial lifecycle proves one-port built assets/API, setup readiness with no workers, the engine's healthy image healthcheck, denied anonymous access, single-use claim/login/logout, the built guided setup route and model-deferral checkpoint persistence, image UID/real volume ownership, SQLite writes, same-volume owner/session/data persistence, closed first-run claim after restart, and clean SIGTERM/SIGINT shutdown. After claim the independent search/email/Sheets roles may run; model/live collection capabilities must stay inactive on the synthetic unconfigured installation. Complete guided setup through reviewed settings and first-run results remains T16's integrated journey; this initial checkpoint check cannot substitute for it.

`--recovery` adds disabled encrypted synthetic model/SMTP/Sheets credentials and a real compiled synthetic PDF. A network-disabled collection container writes a fetch checkpoint and pauses before ingestion. The runner sends actual SIGKILL, then a new network-disabled worker resumes exactly one job while a mocked fetch function refuses any refetch. With the application stopped, one-off image CLI commands create a manifest-verified backup and restore into a separate fresh volume. The restored image must reach owner readiness, retain the password, reject the previous browser session and first-run claim, preserve exact encryption key/decrypted synthetic credentials/document bytes/job observation timestamps and identities, require review for interrupted email, and retain confirmed email and completed Sheets journal/task state without any new email attempt. These checks use synthetic state, no personal installation and no live model/delivery/Sheets provider.

## Database preservation and version contract

The current application initializes its current SQLite schema and the backup manifest records backup format 1; that manifest version is not an independent database schema version. Cross-release database migration and downgrade acceptance are not implemented or verified. This runner proves only backup/restore with the same tested image. Until release-specific upgrade evidence exists, use the exact image version/digest associated with the backup; do not advertise arbitrary newer/older images as interchangeable.

Before changing an image, stop the installation and retain a complete private backup of both databases, exact credential key, settings/source registries, retained uploads and artifacts. Keep the original volume intact until a separate fresh restore has passed owner/readiness/data checks. Restore refuses an existing destination and never resets it. Running an older image against a database already opened by a newer image is unsupported; recovery uses the old image's complete pre-change backup in a new installation instead. There is no silent data reset or promised downgrade compatibility.
