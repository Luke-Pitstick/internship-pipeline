# Subscription resume generation and Resume Matcher contract

The renderer is pinned to [Resume Matcher commit 63fc344a9a59a79db6fa9d96aff188dc9faf545b](https://github.com/srbhr/Resume-Matcher/tree/63fc344a9a59a79db6fa9d96aff188dc9faf545b), inspected October 5, 2026. Its backend package version is 1.3.0. The pipeline performs parsing and tailoring through Codex CLI's saved ChatGPT subscription login; Resume Matcher stores structured content and renders PDFs. It does not need upstream model credentials. Build the pipeline-owned renderer Dockerfile because the original upstream image lacks the structured tailored-import route.

## Codex invocation and subscription boundary

`ResumeService(settings).generate(job, match, profile, checkpoint=None)` uses `CodexResumeGenerator` by default. The worker needs Codex CLI 0.153.0, Node 22 and a writable, persistent `CODEX_HOME` with a saved ChatGPT login. Provision login interactively using the documented CLI flow; the adapter never reads or copies authentication files. `OPENAI_API_KEY` is removed from the child environment and `forced_login_method="chatgpt"` is set, so a stale API-key login cannot silently change billing.

The model is omitted by default because the account's CLI default was successfully probed while the explicitly requested `gpt-6.1-sol` model was unavailable to this subscription. A caller may pass `codex_model` only after separately verifying account support. Schema and prompt revisions, engine identity and an explicit model selection are included in the generation key.

The [documented noninteractive mode](https://learn.chatgpt.com/docs/non-interactive-mode) supports saved authentication and `--output-schema`. The adapter runs `codex exec --ignore-user-config --ignore-rules --ephemeral --skip-git-repo-check --sandbox read-only`, disables web search and tools/features that can execute commands, read files, browse, invoke apps/plugins/hooks or delegate, and requests high reasoning effort. Source text enters through stdin as untrusted data. The CLI runs in a private temporary directory, stdout/stderr are suppressed, structured output is capped at 512 KiB and checked against an extra-forbid Pydantic schema. A hard subprocess deadline kills and reaps the entire process group. Temporary source/schema/output files are removed on completion or failure. Existing project dependencies `pypdf`, Pydantic and httpx are sufficient for the worker adapter.

Master parsing accepts a readable, unencrypted PDF of 1–10 pages and at most 100,000 extracted characters. PDF hyperlink annotations are included because visible link labels can omit their URLs. The prompt requests exact employers, titles, dates, qualifications, projects, links and numerical claims; parsing rejects newly introduced numerical tokens. Tailoring receives the structured master, factual profile, job description, role family and matched fact IDs, and selects supported rows/bullets with at most three bullets per entry. The job description cannot authorize new qualifications. These prompts and automated gates do not prove semantic grounding, so every returned artifact remains a review-needed draft.

## Verified API sequence

All routes begin with `/api/v1`. Native contracts were checked against the pinned [wizard route](https://github.com/srbhr/Resume-Matcher/blob/63fc344a9a59a79db6fa9d96aff188dc9faf545b/apps/backend/app/routers/resume_wizard.py), [resume routes](https://github.com/srbhr/Resume-Matcher/blob/63fc344a9a59a79db6fa9d96aff188dc9faf545b/apps/backend/app/routers/resumes.py), [job routes](https://github.com/srbhr/Resume-Matcher/blob/63fc344a9a59a79db6fa9d96aff188dc9faf545b/apps/backend/app/routers/jobs.py), and [schemas](https://github.com/srbhr/Resume-Matcher/blob/63fc344a9a59a79db6fa9d96aff188dc9faf545b/apps/backend/app/schemas/models.py).

1. Parse the local master PDF through Codex, validate it against the factual profile and cache its structured data before any HTTP mutation. `POST /resume-wizard/finalize` sends `{"state":{"resume_data":ResumeData}}`; other wizard-state fields have defaults. It normalizes and persists a ready master without calling an LLM. Identical content/filename/title is replayed inside an atomic transaction. Upstream permits at most five masters. A profile-supplied master ID instead fetches and fingerprints the remote structured content.
2. `GET /resumes?resume_id={id}` returns `{request_id,data:{raw_resume:{processing_status,content,...},processed_resume,parent_id,is_master,...}}`. Require a ready factual master and validate contacts, protected facts and profile-supported skills.
3. `POST /jobs/upload` sends `{"job_descriptions":["source job description"],"resume_id":"master-id"}`. Its `job_id` array must contain exactly one ID. This route has no idempotency key or job-list reconciliation endpoint.
4. Tailor through Codex, reject explicit factual additions and persist the exact structured result in the disk checkpoint. `POST /resumes/import-tailored` is the pipeline-owned extension. It sends `generation_key` (64 lowercase hex characters), `master_id`, `job_id`, `resume_data` and `title`; it returns top-level `resume_id`, `job_id`, `parent_id` and `processing_status="ready"`. The extension requires a ready master, a job linked to that master, unchanged contact fields and supported standard row identities. It creates one ready nonmaster child using the native transactional `Database.create_tailored_resume`, with an Improvement request ID derived from the generation key. Concurrent identical requests return one child; reuse with different inputs/content/title returns 409. A previously published but deleted child also returns 409 rather than silently recreating it. The extension creates no application tracker card.
5. Fetch the stored child and require the expected `parent_id`; `GET /resumes/{id}/job-description` must identify the expected job. Repeat factual validation on the persisted structured content.
6. `GET /resumes/{id}/pdf?template=swiss-single&pageSize=A4` requires `application/pdf` and a readable PDF. Chromium renders the upstream frontend print route. Template/page/bullet settings and upstream source revision are pinned in `GENERATION_CONFIG` and included in generation keys.

The native upload/improve/provider-config paths are absent from the pipeline client. The default service requires the owned renderer extension; it does not fall back to an upstream API-key provider. Native upstream `/improve` creates a tracker card marked applied, which is why it is not used here. Resume generation never marks the pipeline job as applied.

The inspected routes and extension have no HTTP authentication dependency. Keep this service on a private network. The client disables redirects and environment proxy discovery, bounds response bodies at 16 MiB and redacts bodies from errors. Request timeouts are capped by the remaining generation budget; streamed chunks/polling also check the deadline. A blocked socket can overrun elapsed budget by one bounded operation timeout. Independent worker processes and lease supervision supply the operational recovery boundary.

## Checkpoints and artifact reuse

A supplied checkpoint dictionary is updated in place, but private atomic, fsynced files under `artifact_dir/.checkpoints` are authoritative after interruption. A separate master checkpoint caches the parsed structured master across jobs. Nonblocking OS locks serialize the same generation/master key. One service/client instance belongs to one worker execution thread.

Generation keys cover canonical job ID, exact description, candidate profile revision, master file bytes or fetched remote content, role family, selected fact IDs, backend address, template/page/bullet settings, generator schema/prompt/model identity and validation/publisher/upstream revisions. Artifact manifests contain these identities, remote IDs, selected fact IDs, PDF SHA-256, review status and the serialized artifact. Reuse requires a matching manifest, expected local path and checksum. Missing/corrupt PDF or manifest data is repaired by downloading the known saved child, without another Codex call or new remote creation. A corrupt checkpoint requires inspection because missing IDs may conceal earlier writes.

Before HTTP creation, save `pending=master`, `pending=job` or `pending=tailor`. Master recovery resends the exact cached structured payload to the native atomically replayable finalize endpoint; tailoring recovery resends the exact cached payload and generation key to the owned transactional importer. Neither repeats completed Codex work. Job upload recovery raises `ResumeReconciliationRequired` because the native API cannot safely determine whether an interrupted upload committed. After examining upstream storage, an operator may write the verified job ID into the checkpoint and clear pending. Never clear an ambiguous mutation just because it timed out. Known 4xx rejections clear pending; malformed success, transport failures and server errors conservatively retain it.

`ResumeMatcherError` exposes retryable/ambiguous flags. `ResumeReconciliationRequired` and `ResumeValidationError` are terminal needs-attention states; retain the opening alert and require investigation before explicit retry. An interrupted local Codex transformation may be repeated if no structured output checkpoint exists; completed transformations and published IDs are reused.

## Factual and PDF validation limits

Validation rejects malformed schemas, changed contact fields, unsupported employer/title/date or education/project identities, invented repeated rows, omitted protected values and profile fact-ID mismatches. Explicit skills outside factual profile skills, newly added certifications/languages/awards and numerical tokens absent from master/profile facts fail before publishing or PDF retrieval. Equivalent number reformatting may need manual resolution because the numerical gate is deliberately conservative. Ambiguous semantic rewrites/custom prose produce review warnings, not a false grounding guarantee.

PDF checks reject malformed/encrypted/non-PDF content, unreadable pages, excess pages, missing contacts/protected values, absent populated section headings, omitted identity fields/skills and missing experience/project descriptions. Text origins beyond page bounds generate visual-review warnings. Extracted text cannot establish absence of overlap or ink clipping; a representative rendered-template image remains a live acceptance check. Every usable artifact has `status=review_needed` and an explicit semantic-grounding warning. Proven unsupported claims and failed readability/structure gates never return usable artifacts.

## Deployment and verification evidence

Build `deploy/resume-matcher/Dockerfile` from this repository. It downloads the exact upstream SHA, builds the Node 22 frontend and Python 3.13 backend, installs Chromium and imports the owned route through `pipeline_resume_api:app`. Persist `/app/backend/data`. Use private URL `http://resume-matcher:3000` (or the Render private-service name) and `FRONTEND_BASE_URL=http://localhost:3000`. The pinned startup script hardcodes frontend port 3000 and internal backend port 8000; on Render set `PORT=3000` so service metadata agrees. The renderer container has a nonroot app user with `/bin/bash` and a private `.ssh` directory for authorized diagnostics. No upstream LLM secret is required for this sequence.

Focused synthetic tests cover client payloads, checkpoints, cached transformation replay, lost mutation responses, job ambiguity, manifest repair, factual rejection and PDF checks. CLI tests use bounded synthetic subprocesses for flags/environment, output schema, failure redaction and process-group timeout. A live exact invocation of CLI 0.153.0, forced ChatGPT auth and every disabled-feature flag successfully returned a structured synthetic Alex Example resume through the saved subscription/default model. No personal resume was sent in that smoke test.

`tests/test_resumes_publisher.py` separately exercises the actual pinned upstream ResumeData schemas and SQLite facade, with only the heavy application bootstrap replaced by a test FastAPI instance. Twelve tests passed: six concurrent identical requests produce one child, payload/title/job conflicts fail, changed contacts/identity/repeated rows/master-job mismatch fail, deleted-child replay fails, and no application tracker card is created. Native finalize route tests also prove six concurrent identical master submissions create one master without invoking wizard AI helpers; replay still succeeds at the five-master cap while a new sixth master is rejected. Native finalize uses the actual router/schema/database code with unused turn helpers stubbed. The isolated environment uses upstream's exact FastAPI 0.128.4, SQLAlchemy asyncio 2.0.36, aiosqlite 0.20.0, Pydantic 2.12.5 and pydantic-settings 2.14.2. Run this suite with `RESUME_MATCHER_SOURCE` pointing to the pinned checkout; normal pipeline tests skip it when that external source is absent.

Ruff and mypy pass for owned runtime modules. Full container build/health checks, the installed native finalize route, Chromium rendering, real candidate generation and final visual acceptance belong to the live deployment check; the source/SQLite/CLI evidence above does not by itself prove those live checks. Record the built immutable image digest after deployment rather than treating the mutable upstream 1.3.0 tag as the tested revision.
