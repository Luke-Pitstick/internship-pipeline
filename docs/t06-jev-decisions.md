## Inputs, results and invalidation

The cache identity includes job ID/content hash/opening revision, immutable profile and Jev connection revisions, the tested resolved model, and the complete production rubric hash. Requests pin the tested resolved model; a different response model is invalid output. Relevant profile/preferences changes, posting edits/reopenings, model edits/removal/retests and rubric changes invalidate current results. The matcher reconciles every 30 seconds; owner requests queue immediately. Old task identities consume no new call, and publication checks the current job/profile/connection/model/rubric inside an immediate transaction. Applied/closed jobs cannot publish in-flight results.

Persisted assessments contain all five typed criterion distributions, selected original posting evidence IDs/excerpts, evidence certainty, four score distributions and normalized dimensions, a code-computed weighted fit, recommendation, uncertainty, confirmed candidate evidence and exact model/revision/usage provenance. The request uses the full saved snapshot, retaining confirmed structured education, explicit unknown fields, mandatory constraints and optional preferences; name/email are excluded. Unknown claims and skill interests cannot establish acquired skills. Detail UI escapes provider-source text, displays evidence and provenance, and explains that fit is rubric alignment rather than interview probability.

The T02 automatic-rejection release gate remains closed: every model violation, missing/ambiguous criterion, weak distribution certainty or missing evidence routes to review. A high fit cannot override it. Confidence measures model distribution certainty, not verified correctness. Production v2 reflects the owner preferences contract and is not presented as calibrated by the historical v1 experiment.

## Retry and usage safeguards

The durable production ledger admits at most 3 provider attempts per input identity, 60 per rolling hour and 200 per rolling day, plus 5,000,000 conservative reserved units per rolling day. Reservations survive failure and restart; actual reported tokens are retained and counted when greater than the reservation. Only transient timeout/server/rate-limit failures retry automatically, with the existing queue backoff; exhausted or invalid/authentication results require attention. The owner can retry a failed current identity only while its 3-attempt budget remains. Concurrent calls are serialized, wall time is capped by the tested connection (at most 60 seconds), response bytes are capped at 131,072, and a crashed pending attempt becomes inspectable unknown usage. GET/detail exposes persisted attempt history, including unknown input/output usage.

TypeSafe provides no server output-token-limit field, so these are local admission controls, not a guaranteed provider billing ceiling. Configurable schedules and per-run controls remain T08; connection-test budgets are separate from these production reservations.
