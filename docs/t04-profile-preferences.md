# T04 — Candidate profile and search preferences

Implemented October 6, 2026. The existing Settings page now edits and persists Profile and Job Filters through the authenticated same-origin API. T05's independent AI Models panel and router are mounted in that same page/application.

## Delivered behavior

- The category sidebar keeps the approved separate Settings route. Profile contains personal details, structured experience/project/skill claims, structured education, availability, sponsorship and work authorization. Job Filters separates mandatory country/location/term constraints from preferred roles, locations and skills. Unknown fields remain nullable or empty; sponsorship is explicitly yes/no/unknown. Facts and education have confirmed/unknown states and stable identifiers. Editing preserves those identifiers; removing an entry affects the next revision while retaining its historical snapshot.
- Save and Discard are explicit. The profile/filter draft survives category changes. The UI shows active revision, saved time, unsaved feedback and field errors, focuses the first invalid field, warns before navigation with unsaved changes, and retains a conflicting draft until the owner explicitly reloads the current saved version. AI Models has its own connection revisions and does not display the profile revision label.
- `profile_settings.py` owns strict request models, persistence, candidate projection and its small authenticated router. `GET /api/profile-settings` returns the active snapshot; `POST` requires an `expected_revision`, complete profile and preferences. Saves use `BEGIN IMMEDIATE` and reject stale versions with HTTP 409. Every accepted save appends an immutable row to `profile_settings_revisions` in the existing job SQLite database; triggers reject updates/deletes. No source timestamps, queue histories or application states are rewritten by a settings save.
- Only confirmed claims and education enter the runtime candidate projection. Preferred skills remain interests rather than acquired-skill evidence. Empty eligibility is not converted to false. Multiple confirmed education entries remain separate evidence; the scalar legacy degree field stays unknown rather than selecting one by list order. The revision number participates in the runtime profile fingerprint, including changes to preferences and uncertainty.
- CLI workers read a fresh immutable snapshot at each work boundary and keep one snapshot throughout an individual task/collection pass. Result commits check the active settings revision inside the SQLite write transaction, so an in-flight old-profile match or generated artifact cannot enqueue fresh downstream work after a save. Current worker opening-delivery checks suppress an old-profile payload. Reevaluation and authoritative Jev result storage remain T06.
- Bootstrap dynamically starts newly ready collection/discovery roles after owner claim without replacing the web process. Collection requires sources but neither a candidate profile, model credentials nor a notification destination. Default database, artifact and company paths are confined to the instance data root and passed consistently to CLI children. Operational source/path changes still use documented operator configuration; browser source controls are T07.
- The personal YAML profile loader, `Settings.profile_path`, environment override and example setting were removed. SQLite is the sole runtime candidate/profile-preference authority. Private YAML is neither read for candidate data, silently imported, nor deleted. Existing owners must explicitly back up their old files, remove obsolete `profile_path` from operational settings, and review/re-enter supported facts in the UI. README/deployment instructions explain this boundary. YAML remains only for operational source/path controls pending later tasks.

## Reproduction and limits

Run `PYTHONPATH=src /tmp/internship-pipeline-audit-venv/bin/python -m pytest -q`, `ruff check src tests`, and `mypy src/internship_pipeline`. From `web/`, run `npm run check`, `npm run build`, `npm test`, and `npm run measure`. The space-free Python path is a local symlink to this checkout's virtual environment; ordinary `uv run` equivalents work on a correctly installed checkout. Localhost server tests require permission to bind a loopback port.

Profile/filter saves are real and effective for subsequent worker snapshots. They do not yet apply Jev decisions to the job board; the UI says so. Bootstrap deliberately keeps legacy matching, generation and delivery roles inactive pending T06/T12/notification integration. Document import, model-driven résumé generation, source configuration UI and optional integrations are not represented as finished. No live model calls, private profile reads, external notifications, commits or deployments were performed. Docker execution retains T03's unverified status because no working engine was available for that task; this slice verifies the native process tree and browser/API path.
